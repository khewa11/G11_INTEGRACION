### ADR D3 - Contrato, versionado y evolución 

**Estado:** Aceptado

**Contexto:** Los sistemas de Accesos y Sensores necesitan comunicarse de forma estable, pero sus estructuras de datos podrían cambiar en el futuro. Se debe definir cómo evolucionará el contrato sin romper la integración.

**Alternativas consideradas:**

• Opción A: Versionado explícito en la ruta para REST y uso de las reglas de compatibilidad de esquema en Protocol Buffers

• Opción B: Usar versionado en cabecera HTTP para mantener la URL limpia.

• Opción C: No versionar nunca y aceptar solo cambios puramente aditivos.

**Decisión:** Se elige la opción A.

**Justificación:** Para la API REST, el versionado en la URL es la opción más usada, es fácil de enrutar en un Gateway y es trivial de documentar mediante OpenAPI. En cuanto a gRPC, Protobuf ofrece compatibilidad hacia atrás y hacia adelante de forma nativa. Si mañana hay que agregar un campo “stock”, se añade con un número de etiqueta nuevo; los clientes antiguos simplemente ignorarán ese dato porque no conocen la etiqueta numérica, evitando un error de compilación o ejecución.

**Costo aceptado:** Cualquier cambio incompatible en la API REST obligará a publicar un nueva versión. Ambas versiones deberán servirse en paralelo apuntando a la misma lógica interna. Además, exigirá instrumentar mediciones para saber qué clientes siguen usando la versión anterior antes de poder apagarla.

**Consecuencias:** Los cambios compatibles se harán silenciosamente en la versión antigua. Si se requiere un cambio incompatible, se creará la versión nueva. Los consumidores de la antigua se enterarán del cambio inminente porque sus respuestas HTTP comenzarán a incluir la cabecera Deprecation y un enlace a la guía de migración meses antes del apagado definitivo.
