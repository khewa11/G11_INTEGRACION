### ADR D1 - Estilo de integración y descomposición 

**Estado:** Aceptado 

**Contexto:** Existen dos sistemas históricamente desconectados que necesitan integrarse. Sensores administra el estado físico (plazas) y Accesos la parte comercial (vehículos y tickets). Se debe decidir cómo separar responsabilidades, qué datos mantener en cada lado y cómo se comunicarán.

**Alternativas consideradas:**

• Opción A: Unir ambos sistemas bajo una sola base de datos y un solo despliegue. Cuesta autonomía técnica. 

• Opción B: Un servicio de “Lógica” y otro de “Datos”.

• Opción C: Separar por fronteras de negocio, cada uno con su base de datos propia, comunicándose síncronicamente vía invocación remota (gRPC/REST).

**Decisión:** Se elige la Opción C.

**Justificación:** Se optó por Bounded Context según el dominio del negocio. Sensores gestiona la alta volatilidad del recinto físico de forma aislada de Accesos, que gestiona el ciclo de vida del ticket. Esta descomposición asegura el despliegue independiente y el aislamiento de fallas de base de datos.

**Costo aceptado:** Se renuncia a transacciones ACID globales y consultas tipo *JOIN*. Aceptamos la duplicación controlada de datos: el campo *sector_id* pertenece al dominio de Sensores, pero debe guardarse redundante como referencia en la tabla tickets de Accesos. Además, se introduce latencia de red al tener que invocar a Sensores para validar cada ticket emitido.

**Consecuencias:** La integridad referencial debe manejarse por código. Ante un registro nuevo, Accesos depende obligatoriamente de invocar la red hacia *sensores:50051*.
