### ADR D4 - Resiliencia y modos de falla

**Estado:** Aceptado

**Contexto:** La API de Accesos depende síncronamente del servicio de Sensores para verificar la disponibilidad antes de hacer POST en tickets. Como toda llamada a través de red puede fallar, la API de Accesos debe decidir cómo comportarse ante la caída o latencia del servicio interno.

**Alternativas consideradas:**

• Opción A: No captura la excepción y que la API falle internamente.

• Opción B: Capturar el error y emitir el ticket igual asumiendo disponibilidad, para no frenar el ingreso.

• Opción C: Capturar el error y responder con un mensaje de servicio no disponible.

**Decisión:** Se elige la Opción C.

**Justificación:** Según la semántica HTTP, la familia 500 indica culpa del servidor. Específicamente, el código 503 informa al exterior que la API está viva, pero el servicio interno está temporalmente inactivo. La Opción B causaría un problema físico gravísimo de sobrecupo, y la Opción A ocultaría el origen del error de infraestructura. 

**Costo aceptado:** Acoplamiento temporal extremo. Ante la caída de Sensores, el servicio Accesos queda totalmente inoperativo para la emisión o reversión de tickets, paralizando la barrera de entrada.

**Consecuencias:** Cualquier cliente web o físico consumiendo esta API REST debe saber interpretar el código 503 y accionar un mensaje de Estacionamiento sin conexión. Si la latencia llegara a ser un problema a futuro, la próxima decisión sería implementar un timeout en el cliente gRPC para no agotar los threads del servidor FastAPI.
